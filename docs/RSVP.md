# Saved guest RSVP

## Organiser corrections

Admin/Manager members can open guest details and select **Record or correct RSVP** to record a phone response, correct attendance, or reset to Pending. An explicit confirmation is required. `PUT /api/v1/weddings/{weddingId}/guests/{guestId}/rsvp` requires member authentication, Origin/JSON/custom request header and the guest's expected version; it returns `{version,rsvp}` with the member-visible server-owned updater metadata. Attending requires 1 through the current allocation; Pending/Not attending store zero. Organisers may correct attendance without active invited events or with a disabled guest invitation. Authority comes from live membership, not the guest link.

Identical PUT replay acknowledges the current response without rewriting attribution/timestamps, even with an old observed version; conflicting stale answers return 412. Membership and wedding scope are rechecked under the coordination write before either outcome. Changed responses record server time, `updatedByKind=member` and the authenticated member ID. Reset Pending has a response timestamp; untouched Pending remains null.

Both organiser PUT and correction-bearing PATCH require atomic fixed-window admission before starting a transaction or writing the wedding fence. They share 20 attempts per minute per authenticated account within a wedding, and 60 per wedding across accounts. The budget spans guest targets, endpoint methods and URL ID casing; identical PUT replays consume admission too. Authoritative account/wedding identifiers are SHA-256 hashed in the existing rate-limit buckets; no guest token, raw identifier or new provider configuration is required. Exhaustion returns `429 RATE_LIMITED` with Retry-After. The form disables another correction until that delay expires and an explicit reload clears confirmation. The limiter operates outside the product transaction, so rejected work cannot touch the fence; admission never relies on TTL cleanup.

To lower an allocation while correcting attendance, the form sends a single PATCH `{maxPartySize,rsvp}`. The allocation must decrease and satisfy the deployment limit; corrected attendance must fit. PATCH retains ordinary version conflict semantics. Lowering below attendance without a correction is rejected. Unchanged historical allocations remain valid even above a lowered deployment cap. Unrelated fields and existing event assignments are preserved; explicitly supplied event assignments must be active and wedding-scoped.

Stale/uncertain corrections block further saves until an explicit GET reload synchronises the saved response/allocation and clears confirmation. Directory data is explicitly reloaded; dashboard counts derive from stored records on fresh reads. Run `npm run check:rsvp:organiser` for isolated integration checks and `npm run check:rsvp:browser` for desktop/mobile correction and recovery workflows. Guest RSVP/link/context regressions remain covered by the existing commands.

Personal invitation holders can save one overall `attending` or `not_attending` response at `/invitation`, without an account. Attending requires an integer from 1 through the guest's current `maxPartySize`, including the named guest. Declining stores zero. Existing allocations remain authoritative if the deployment's new-guest allocation cap is later lowered. Organiser corrections and resets are implemented as described above; delivery remains deferred.

`PUT /api/v1/guest/rsvp` accepts `{invitationContext, status, partySize}` and requires the live invitation cookie, configured Origin, JSON content type, `X-KP-Request: 1` and `X-Expected-Version`. The response is `{data: {version, rsvp: {status, partySize, respondedAt}, capabilities: {canRespond, canAttend}}, meta: {requestId}}`, with private/no-store and resource-version headers. Contact details, organiser identity and bearer material are excluded.

The invitation view includes an opaque `invitationContext`: a purpose-separated HMAC binding wedding, guest and invitation token version. It is a display binding, not an access capability, and exposes no raw record identifiers or bearer token. Each form sends the context from its rendered view. Before any transaction or identical-replay acknowledgement, the service checks it against the authenticated guest grant. Opening a different invitation in another tab cannot redirect an older form's save to the new guest, even when versions and answers match. A mismatch returns `409 INVITATION_CONTEXT_CHANGED` without a product write; saves remain blocked until explicit reload replaces the displayed invitation and form together.

The service checks live access before input/revision errors, then rechecks cookie expiry, guest/wedding scope, enabled state and token version inside the short snapshot/majority transaction after the wedding coordination write. A changed answer increments the guest version and records server timestamps and `updatedByKind=guest`; identical replay returns the current answer/version without changing response timestamps, even with an old observed revision. Conflicting stale answers return 412. Identical replay never bypasses revoked or expired access.

Only active invited events from the same wedding permit new attendance. With none remaining, saved attendance is preserved and identical replay is acknowledged; a changed attending answer returns `409 NO_ACTIVE_INVITED_EVENTS`. Guests can still decline. Wedding dates do not automatically expire invitations.

Admission reuses the existing atomic fixed-window rate-limit storage, with separate RSVP action namespaces: 60 attempts per minute per trusted IP (shared local bucket without the trusted-header configuration), and 20 per captured invitation grant. Subjects are HMAC-hashed; exhaustion returns 429 with Retry-After. The browser observes that delay before reloading/retrying.

The form shows confirmation only after a successful response. Network/5xx uncertainty and revision/event conflicts block another save until an explicit GET reload synchronises the entire invitation and form. No automatic PUT retry occurs. The backend's identical-replay rule provides an additional safeguard. Refreshing or reopening the link loads the durable answer.

The dashboard derives response counts, status counts and expected attendees from wedding-scoped guest records. Expected attendees sums attending party sizes, rather than allocations; no duplicated counters are stored. The guest directory continues to show saved responses and its metrics describe the loaded/filtered view. Updates appear on a fresh read/navigation; there is no realtime polling.

Run `npm run check:rsvp`, `npm run check:rsvp:browser`, `npm run check:invitations`, `npm run check:guests`, `npm run check:contracts`, `npm run lint`, `npm run typecheck` and `npm run build`. Replica-set and browser checks use synthetic disposable data, with no Atlas/provider requests. Browser tooling follows `docs/GUESTS.md`. No new dependency, provider or credential is needed.
